# Prioritized, Dependency-Ordered Implementation Plan

**Date:** 2026-11-03  
**Baseline:** [architecture.md](./architecture.md), including the seven user-agreed revisions in [design-review.md](./design-review.md).  
**Requirements:** [requirements.md](./requirements.md).

## 1. Planning rules and current status

- This is a plan, not a record of completed implementation. No task below is assumed complete.
- User agreement on the design revisions does not resolve bank policy, business definitions, source feasibility, or measurable service targets.
- Complete discovery, contract validation, and bank approvals before production implementation. Unsupported source/identity capabilities require design revision or source enhancement, not a silent workaround.
- Keep one modular backend initially; reuse existing identity, core banking, session, edge, and event infrastructure where supported. Do not introduce extra microservices, a password database, or an authoritative balance cache.
- Web/SSE tasks are conditional on channel and integration approval. If another channel is selected, revise the relevant transport/client tasks before implementation.
- **P0:** Prerequisite, risk-critical, or acceptance/release gate; prioritize over ready P1 work.
- **P1:** Required supporting delivery work; not optional and not a scope reduction.
- **Ready:** Can begin now; means prerequisite discovery/approval work, not approved production coding.
- **Blocked:** Cannot start until every listed prerequisite is completed and its exit evidence accepted. Dependencies apply transitively.
- Rows are in topological order: every dependency appears earlier. Row order does not create a dependency; independent tasks may proceed in parallel.
- Suggested owners are roles to assign. No effort estimates, dates, numeric SLAs, technology selections, or bank approvals are invented.

## 3. Dependency order and parallel work

These are scheduling groups, not additional prerequisites:

1. **Start now:** T01 through T06 can run independently. T06 is mandatory despite P1 priority.
2. **Contract and approval sequence:** T07 -> T08 -> T09. Any failed feasibility/approval gate blocks all production implementation.
3. **Parallel foundations:** T10 and T11 after T09.
4. **Parallel module tracks:** T12, T13, and T14 after the foundations. T17 can start once T10/T13 are complete; it does not need to wait for balance retrieval. T19 can start once T11/T14 are complete; it does not need to wait for client presentation.
5. **Account path:** T15 -> T16. T18 joins T16/T17.
6. **Update path:** T20 joins T16/T19. T21 and T22 can then progress independently when their other listed prerequisites are complete.
7. **Integrated client:** T23 joins T18/T21/T22; T24 also requires T12.
8. **Independent verification:** T25, T26, and T27 can run in parallel after T24, subject to isolated test environments and coordinated load/fault activity.
9. **Release sequence:** T28 joins all three verification tasks; T29 follows T28.

**Dependency backbone:** approvals -> foundation -> session/core integration -> authorized snapshots -> synchronized updates -> complete client/staging -> all acceptance gates -> release. There is no estimated time-based critical path because task durations have not been established.

## 6. Scope exclusions

This plan does not include registration, password recovery, transaction history, transfers, payments, account opening/closure, other account types, or new banking capabilities. Any necessary source-system enhancement identified during feasibility is a separately owned prerequisite, not permission to expand the customer feature silently.
