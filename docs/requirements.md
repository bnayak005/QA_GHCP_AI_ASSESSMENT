# Requirements: Banking Login and Account Balance Viewing

## 1. Purpose and source

**Source:** Banking_User_Story.docx, "Simple Banking Application User Story".

**User story:** As a bank customer, I want to log in to the banking application and view my account balance so that I can track my available funds at any time.

**Business value:** Give customers quick access to financial information, improve customer satisfaction, and reduce balance-related calls to customer support.

**Primary actor:** Bank customer.

**Supporting systems:** Customer authentication service and authoritative account/balance service. These are logical dependencies, not prescribed implementation technologies.

### Source acceptance criteria

| ID    | Acceptance criterion                                         |
| ----- | ------------------------------------------------------------ |
| AC-01 | The customer can log in using a valid username and password. |
| AC-02 | The system displays account balances after successful login. |
| AC-03 | The customer can view savings and checking account balances. |
| AC-04 | The balance information is updated in real time.             |
| AC-05 | An error message is shown for invalid login credentials.     |

## 2. Scope and requirement status

**In scope:** Username/password login, invalid-credential feedback, authenticated access to customer balances, savings and checking account balances, and real-time balance updates.

**Not specified by this story:** Registration, password recovery, funds transfers, payments, transaction history, account opening/closure, profile management, and other account types. These require separate scope approval.

Requirement statuses:

- **Explicit:** Directly stated in the story or acceptance criteria.
- **Derived:** Necessary supporting behavior inferred from the story; requires stakeholder validation.
- **Proposed:** Recommended operational, security, or usability requirement; not an approved commitment.

All requirements use "shall" to express the intended behavior. Derived and proposed requirements remain subject to approval. No numeric service-level target is asserted as a source requirement.

## 7. Assumptions and dependencies

- Customer identities and savings/checking accounts already exist; account creation is not part of this feature.
- Authentication and authoritative balance services are available integration dependencies. Their contracts, access controls, and failure responses must be confirmed.
- Viewing balances is read-only; this story does not authorize transaction initiation or account-data modification.
- Displaying all eligible savings/checking accounts is a reasonable proposed interpretation, but multiple-account selection and joint-account entitlement rules remain unresolved.
- Stakeholders will approve derived/proposed requirements and measurable quality targets before these become delivery commitments.

## 9. Readiness for sign-off

The five source acceptance criteria are covered by FR-01 through FR-06 and AT-01 through AT-05. Before implementation sign-off, stakeholders must resolve the balance definition and real-time threshold, approve the derived/proposed requirements, and agree measurable operational targets. Compliance obligations must be confirmed against the bank's actual jurisdiction and policies.
